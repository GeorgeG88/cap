# Post-test improvements — 2026-11-16

Full backup of the pre-change code is in this `_rollback/` folder (`app/`, `deploy/`,
`manage.py`). To roll back everything: copy those back over the project and delete
`_rollback/`. Each change below is independent and can be reverted on its own.

## 1. Brute-force rule counts per destination port  (app/core/detection.py)
Problem: every port scan also raised a "Brute-force attempt" alert, because the rule
summed connections across all auth ports (a scan touching 21,22,23,110,143,389 added up
to the threshold).
Change: added `group_for()`/`src_for()` to the base `SlidingWindowRule` (counters and
episodes are now keyed by a "group", default = source IP). `BruteForceRule.group_for`
returns `(src_ip, dst_port)`, so the rule only fires when ONE service gets >= threshold
connections. `Episode` gained a `src_ip` field; `_detection()` now reads it.
Test: tests/test_detection.py::test_brute_force_counts_per_port_not_across_ports
Rollback: restore app/core/detection.py and remove that test.

## 3. Warn when UFW logging is rate-limited  (monitor.py, __init__.py, base.html)
Problem: the first brute-force test silently failed because UFW `logging high` throttles
allowed-connection logging to ~3/min, so the attack was never fully logged.
Change: `ufw_logging_level()` in app/core/monitor.py reads LOGLEVEL from /etc/ufw/ufw.conf.
The context processor in app/__init__.py exposes `ufw_logging_level` /
`ufw_logging_rate_limited` to templates. base.html shows a warning banner while live
monitoring is running and the level is off/low/medium/high. On non-firewall hosts the
file is absent, the helper returns None, and no banner shows.
Rollback: restore those three files.

## 5. Show the real detection time  (reporting.py, alert_detail.html)
Problem: first_seen is pulled back to the window start, so it is not a true detection time.
Change: the alerts CSV now includes a `detected_at` column (the alert row's existing
created_at), and the alert page shows "Detected at". No schema change (created_at already
existed).
Rollback: restore app/core/reporting.py and app/templates/alert_detail.html.

## 4. Group related alerts into incidents  (models.py, __init__.py, alerting.py, reporting.py,
##    web/alerts.py, templates/alert_detail.html)
Problem: one attack trips several rules, so one SYN scan produced 4 alerts and the queue had
27 alerts from 8 attacks.
Change: added `Alert.incident_id` (indexed). `AlertManager._incident_for()` reuses the incident
of a recent alert from the same source (window = incident_window_minutes, default 5), so a new
alert joins that incident; otherwise it starts its own. New setting `incident_window_minutes`.
`ensure_columns()` in app/__init__.py auto-adds the column to an existing database on startup
(verified: existing rows preserved). The alerts CSV has an `incident` column; the alert page
shows the incident with a link to `/alerts/?incident=<id>` (new filter in web/alerts.py).
Tests: test_alerting.py::test_alerts_from_same_source_share_one_incident
Rollback: restore the six files; the leftover incident_id column is harmless (ignored).

## 2. Read sshd's auth log to catch SSH brute-force  (NEW core/authparser.py; pipeline.py,
##    monitor.py, models.py, __init__.py, manage.py, web/admin.py, templates/monitor.html,
##    templates/settings.html)
Problem: a brute-force against the allowed SSH service evaded the firewall rules, because UFW
rate-limits allowed-connection logging and nmap reused connections.
Change: new module app/core/authparser.py parses /var/log/auth.log (Failed password / Invalid
user / Accepted) and an AuthBruteForceDetector counts failed logins per source IP, emitting the
same Detection objects the firewall rules use. A new rule "ssh_auth_bruteforce" is seeded into
the rules table (threshold 5 / 120s / high, editable on the Rules page; the firewall engine
ignores it). AuthPipeline (pipeline.py) runs it and raises alerts without storing firewall events.
The live monitor (monitor.py) now ALSO tails the auth log in a second, isolated thread: if it
cannot start, the firewall monitoring is unaffected and a note is shown. New settings
auth_monitor_enabled / auth_log_path (Settings page). CLI: `python manage.py analyze-auth <file>`.
The Live monitor page shows auth-tail status.
Tests: tests/test_authparser.py (6) and
tests/test_web.py::test_live_monitor_detects_ssh_bruteforce_from_auth_log.
Note: the live-monitor tests now use a file-backed SQLite DB (new live_env fixture) so the two
tail threads each get their own connection, as in production.
Rollback: delete app/core/authparser.py and tests/test_authparser.py, restore the other files,
and remove the seeded ssh_auth_bruteforce row (or just disable it on the Rules page).
